## 2. What the project is trying to establish

FaithfulRecon evaluates whether internal 3D Gaussian Splatting signals deserve to guide interventions in static scenes with sparse or restricted training views. A score that predicts errors may still select useful geometry for deletion. The evaluation therefore separates three questions:

| Dimension | Question | Main owner |
|---|---|---|
| D1: failure association | Does a signal rank benchmark failure/under-observation labels correctly? | Tuấn Khải; labels from Trường Thịnh |
| D2: intervention response | Does removal produce a measurable, localized response in the expected direction relative to random removal and re-optimization noise? | Huy, with Trường Thịnh's analysis |
| D3: held-out predictive validity | Does a signal predict reconstruction error on views excluded from training? | Phát |

RQ4 compares these dimensions: good D1 or D3 performance may coexist with poor D2 behavior. Your second-order signals enable H1 and the signal comparisons; your D3 pipeline supplies the missing evidence for RQ3/RQ4. A negative result can be a valid research outcome.

The benchmark deliberately separates `m_i`, an under-observed condition assigned using cameras/reference geometry, from `f_i`, a geometric failure outcome involving distance, opacity, and held-out contribution. Neither should be silently substituted for the other.

## 6. This week: W3, 12–18 October — implement and validate the estimator

### 6.1 Mathematical target

For training view `c`, flatten the rendered RGB image into `I_c`. Let `J_{c,i}` be its Jacobian with respect to the selected parameters of Gaussian `i`. Compute:

```text
F_i = sum_c J_{c,i}^T J_{c,i}
v_{c,s}: independent Rademacher entries over every pixel and RGB channel
g_{c,s,i} = derivative of sum(v_{c,s} * I_c) with respect to theta_i
F_hat_i = sum_c [ (1/S) * sum_s g_{c,s,i} g_{c,s,i}^T ]
E[F_hat_i] = F_i, because E[v v^T] = Identity
```

Differentiate the rendered image projection. An outer product of the L1/SSIM training-loss gradient estimates a different object. Averaging all samples across all views without correcting the view count also changes the specified sum. Use training cameras only.

The estimator is a per-Gaussian Gauss–Newton block. Its equality with a probabilistic Fisher requires the stated observation-noise model; it is not the exact Hessian of the repository's L1/SSIM objective. Treat inverse blocks as a block approximation, not as the marginal covariance obtained by inverting the full scene matrix.

### 6.2 Implementation specification

Target API already exists:

```text
fisher_blocks(ctx, params=("means",), n_samples=4) -> Tensor[N,D,D]
```

Implement generic selection from `model.params`, with row-wise flattening and concatenation in the requested order. The main required calls are means-only `(N,3,3)` and means plus log-scales `(N,6,6)`. A generic implementation also prepares for the W4 all-parameter Fisher trace, including the scalar opacity field.

Requirements:

1. Render using the existing differentiable `GaussianModel.render`/PyTorch backend. Do not call an optimizer or change Gaussian order/count.
2. Form independent pixel/channel probes, differentiate their image dot product, concatenate each Gaussian's parameter gradients, and accumulate the full small outer product. The 6×6 block must retain mean/scale cross terms.
3. Average over probes per view, sum over views, and return detached finite blocks on the model's device. Keep accumulation precision explicit.
4. Store only the running blocks and one view's render graph; release graph history when finished. Never retain the production per-pixel Jacobian or every sample gradient.
5. Cache by parameter tuple/sample count and all supported options that affect the result. Treat a `SignalContext` as tied to one immutable checkpoint/camera/backend configuration.
6. Use an estimator-specific deterministic generator. The existing `ctx.generator` is also consumed by random/visibility signals, so blindly reusing its evolving state can make the estimator depend on signal execution order.
7. Reject invalid sample counts or parameter names. Define the behavior for empty camera lists and non-contributing Gaussians. A Gaussian with no image influence should produce a zero information block; damping/fallback scores belong to the downstream signals.
8. Prefer `torch.autograd.grad` so scoring does not populate or accumulate training `.grad` buffers. Test that model values and pre-existing gradient state are preserved.

**Parameterization decision:** the local model stores `log_scales`, then renders `scales = exp(log_scales)`. A block with respect to log-scale is not interchangeable with a block with respect to activated scale. Keep the W3 native block explicitly named/documented. If the W4 PUP recipe needs activated-scale derivatives, convert using the chain rule or use a documented separate parameter basis. This decision affects determinant-based rankings and damping.

For `l = log(s)`, `g_s = g_l / s`. With parameter order `(mu,l)`, use `A_i = diag(1,1,1,1/s_x,1/s_y,1/s_z)` and `F_(mu,s) = A_i^T F_(mu,l) A_i`. Apply damping after choosing the parameter basis; copying the same epsilon between bases does not preserve the score.

## 8. D3 issues to record now, then implement in W6–W7

D3 will attribute held-out pixel error to Gaussians through feature gradients, measure Gaussian-level correlation/AUROC, and evaluate pixel maps via sparsification/AUSE. Record these integration issues now so they do not surprise the later implementation:

- The PyTorch renderer's `contrib` is the exact sum of blending weights. The gsplat adapter substitutes footprint area times opacity. The D3 numerator/denominator identity therefore needs the PyTorch backend or another verified exact denominator; a backend switch is not automatically equivalent.
- For feature renders, use a background with the same channel count. Detach the RGB error map before using it as attribution weights. Exclude or explicitly mask zero held-out contribution instead of assigning a fabricated observed error.
- Raw rendered scores include opacity/background effects. Specify whether maps are contribution-normalized, define the eligible pixel mask, and apply the same convention to random/oracle curves.
- Positive monotonic transforms preserve per-Gaussian rankings, but they need not preserve rankings after alpha-blending scores into pixel maps. The assignment's rank-invariance argument for dropping `exp(-lambda * ...)` needs that qualification for pixel AUSE. Prevent exponential underflow ties if transforms are compared.
- Keep signal construction on training views. Any calibration or hyperparameter fitting using held-out views needs a separate evaluation split; do not tune on the final D3 test views.
- Match the eventual D1–D2–D3 join by scene, view condition, checkpoint/hash, seed, signal definition/parameters, backend, and protocol version. Label AUROC versus `f_i` as failure-label association even when included in the D3 report.

These are later design requirements; implementing D3 this week would put the estimator deadline at risk.
